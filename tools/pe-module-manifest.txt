# Windows PE modules a DirectX-era title imports that app/Madeira/{arch}-windows
# does not ship yet.
#
# Format: `<kind> <module-stem> <component>`, `#` starts a comment.
#
#   wine    -- Wine builds it (dlls/<module>), so scripts/build-wine-pe-modules.sh
#              produces it from the pinned tree. A missing one is a defect.
#   native  -- Wine does not implement it at all. The only source is Microsoft's
#              redistributable, which tools/fetch-directx.sh extracts into
#              app/Madeira/x86_64-directx/ for the x64 session. Reported by the
#              build script, never failed: it is a component, not a build.
#
# The set is not a guess. Every `wine` row is a DLL named by Winlator's own
# component definitions (brunodev85/winlator-app a030f552,
# app/src/main/assets/wincomponents/wincomponents.json) -- a decade of
# accumulated "this title needs this module" evidence -- cross-checked against
# what this pinned Wine tree can build (dlls/*/Makefile.in). The component
# column names the entry that asks for the module, so a failure names its cause.
# The *-legacy groups and gamecore/video/directshow/mediafoundation/direct2d are
# additions; each group carries its reason in the comment above it.
#
# This file deliberately does not alias. DLLAliases.h used to paper over the
# d3dx9/d3dx10/d3dcompiler generations with the newest shipped module, which is
# wrong and measurably so -- see the *-legacy comments. An alias is only allowed
# where every export of the aliased-away module is present in the target, and
# tools/check-dll-aliases.py proves that from the real binaries.
#
# Inspect the current gap with:
#   python3 tools/check-pe-module-set.py --report

# --- direct3d ---
# Winlator's DirectX component. Wine implements a lot of this as stubs -- 19 of
# d3dx11_43's 44 exports return E_NOTIMPL, including
# D3DX11CreateShaderResourceViewFromFile{A,W}, which is the call a DX11 title
# makes to load a texture. The real implementations come from the DirectX
